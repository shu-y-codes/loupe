# 05 — UI

**Goal.** Shared chrome, persona selector, Summary / Specifics, upload preview,
named-box help. Widgets stay thin — call the API or shared services.

**Status.** pending

Amended 2026-09-06 after readiness review against `specs/loupe-ui-design.md` and the slice 4
build. Five prerequisites, none of them UI code: the missing dependency; two backing-data
gaps the wireframes need and slice 4 did not ship; the process wiring; and the page-test
harness. See **Sequencing** below.

Source of truth is already `specs/loupe-ui-design.md` (solution brief §12 is pointer +
invariants). No note promotion required for chrome.

## Done when

### Prerequisites — not UI code

0. **`streamlit` added and locked.** It is named in the solution brief (§6) and in this
   plan, and is in neither `pyproject.toml` nor `uv.lock`. Every done-when below is blocked
   on it, exactly as slice 4 was blocked on `fastapi` / `python-multipart` / `httpx`
   ([04-api.md](04-api.md), done-when 2). It goes in `[project.dependencies]`, not an
   optional extra: slice 7 is a README walkthrough someone runs end to end, and one
   `uv sync` is the difference between that working and not. No API-only consumer exists to
   protect from the transitive weight.

1. **`GET /v1/dq/changelog` — the changelog panel has no route today.** Trader Specifics
   carries a Changelog panel with click ↔ chart mark binding
   (`specs/loupe-ui-design.md`, Trader Specifics), Analyst carries an engine changelog, and
   the solution brief lists it for both personas (§2, §12). `dq.cleaning_action` has held the
   rows since slice 2 ([ddl.sql:195](src/loupe/data/ddl.sql#L195)) with no read path, and
   neither `specs/api-contract.md` §6 nor its "v1 vs extension (routes)" table has a
   changelog endpoint. A reader in `quality` owns the query and a route in
   `api/routes/dq.py` calls it. Two places in the
   contract change, not one: §6 gains the route and its shape, **and** the DQ row of the
   "v1 vs extension (routes)" table gains it. A v1 route missing from the v1 route table is
   the drift that table exists to catch.

   **It returns the aggregated grain — rule × trade date × action, with a count — not one
   row per record.** `dq.cleaning_action` is per record and carries neither `contract_id`
   nor `trade_date`; both come from joining `stage.market_record`, which has them
   ([ddl.sql:96-114](src/loupe/data/ddl.sql#L96)). The Trader panel row is a count
   (`CMP.* 2025-06-12 excluded 4 open slots`), so a per-record route would leave the
   widget doing the aggregation that the layer table puts outside `ui`
   (solution brief §6). Read-only and paginated. Scope is the latest succeeded run by
   default, resolved the way `/dq/summary` already resolves it
   ([dq.py:73-79](src/loupe/api/routes/dq.py#L73)), with an explicit `run_id` accepted so a
   past run stays inspectable.

   Deriving the panel in the UI from findings plus severity is the rejected alternative: the
   engine's cleaning policy has two documented exceptions to the severity default
   ([cleaning.py:11-15](src/loupe/quality/cleaning.py#L11-L15)), and restating them in a
   Streamlit callback is the non-goal below. Cutting the panel is the other alternative and
   costs more than it saves — the changelog is the evidence for locked decision 1
   (immutable raw, derived clean view, reproducible from file plus ruleset; solution brief
   §3). A demo whose thesis is defensibility should not ship with the audit trail cut.

2. **Contract-grain rollup and per-contract callout on `GET /v1/dq/summary`.** The Score
   column is already served: `/v1/dq/summary` with no `contract` filter returns per contract
   × frequency `slices[]`, each with a weighted `overall`
   ([dq.py:137-146](src/loupe/api/routes/dq.py#L137-L146)). Two things the Summary table
   needs are not in that response, and both are fields on a call the page already makes —
   no new route:

   - **Rollup.** Every persona's inventory is one row per contract; a contract holding both
     frequencies yields two slices. The rollup rule is **min across slices** — a contract is
     as trustworthy as its worst frequency — composed in `quality` and returned as
     `contracts[]` alongside `slices[]`. A record-weighted mean is the alternative and is
     worse here: it lets a large clean minute tape bury a broken daily file, which is the
     defect this corpus is full of. The page-level `overall_score` is left alone; it is an
     unweighted mean of slices today ([dq.py:143](src/loupe/api/routes/dq.py#L143)) and
     changing it is a wider contract change than this slice should carry.
   - **Callout.** Each `contracts[]` row carries **two** one-line callouts, because the
     personas make different selections over the same findings. `top_issue` is the
     contract's worst issue of any kind — Analyst's Top issue, and Trader's Warning.
     `settlement_issue` is Risk's **Closing-day** column, which is a statement about the
     session's settlement record: its wireframe values are close outside H–L, missing EOD
     bar, duplicate settlement and off-tick close, never `TIM` smear or an open gap.
     `_top_issues` is scope-wide today; both fields are that query grouped one level finer,
     the second filtered. Per-contract `finding_count` needs nothing new —
     `/v1/dq/metrics?group_by=contract` already carries it.

     **The filter is a named set in the catalogue, not a list in a widget.** Nothing on
     `dq.dq_rule` separates a settlement rule from any other
     ([ddl.sql:132-147](src/loupe/data/ddl.sql#L132)), so `SETTLEMENT_RULES` joins
     `DEDUPE_DROP_RULES` and `NEVER_EXCLUDE_RULES` in
     [catalogue.py](src/loupe/quality/catalogue.py#L509) — already the home for a named set
     of rule IDs with a documented reason — and is applied with `frequency = 'daily'`,
     since `VAL.OFF_TICK_PRICE` on a minute record says "off-tick price", not "off-tick
     close". Membership and rationale are spec'd in `specs/dq-rules-and-scoring.md` §11.6.

     **Both fields ship on every row rather than behind a `?callout=` parameter.**
     `specs/api-contract.md` §8 is already law on this: personas are a UI view selector and
     nothing in the contract is persona-aware. A parameter would make the endpoint
     persona-shaped to save one string per contract row.

   - **Trend.** The fourth Risk KPI is a sparkline of settlement reliability over trade
     dates. That phrase was undefined — it appeared once, in a tooltip — and the page and
     Risk wireframes disagreed on whether the tile was *DQ trend* or *Settlement trend*.
     Both are settled in `specs/loupe-ui-design.md`: it is **daily completeness per trade
     date**, which is not a new metric (one expected daily record is one expected settlement
     session, so it is §11.1's `completeness` dimension at `frequency = 'daily'`), and the
     tile is *Settlement trend* everywhere. `mart.dq_metric_daily` already stores it per
     contract × date × frequency × dimension, so the only change is a **`dimension` filter
     on `GET /v1/dq/metrics`** — `group_by=day` averages the dimensions together today
     ([dq.py:268-292](src/loupe/api/routes/dq.py#L268)) and cannot isolate completeness.

   - **Status.** `ATTN` / `OK` drives the Risk inventory and the Book-hit KPI, and appeared
     only inside wireframes with no rule. Settled as **any open `error` or `critical`
     finding**, not a score cut: §11.5 makes the score a navigation index rather than a
     grade, and those two severities are already the ones default cleaning acts on, so
     `ATTN` means "something here was excluded or blocked". Definition and consequences in
     `specs/loupe-ui-design.md`, Risk → Summary. No API change — severity is already on
     every finding.

   Exposing [`worklist()`](src/loupe/quality/scoring.py#L402) as a route would serve the
   callout *and* give the Specifics **Impact** column a real `score_if_resolved` number
   instead of prose. It is the right companion to the Analyst view and belongs with slice 6,
   not on the critical path to the Summary table.

3. **The UI reaches the API over HTTP.** `LOUPE_API_URL`, default
   `http://127.0.0.1:8000/v1`, read by a thin `src/loupe/ui/client.py`; stubbing that one
   module is what makes done-when 4 possible. The README documents starting uvicorn and
   streamlit. The alternative — `ui` imports the FastAPI app and calls it
   in-process via `TestClient` — is one process and no port, but it fuses the two layers the
   architecture separates (solution brief §6) and makes the thin-client boundary
   untestable as a boundary.

4. **Pages are testable, and §13 says how.** The Tests section below asserts page
   behaviour — persona switch changes the Summary columns, no apply/override control exists
   in the tree — and the testing strategy table (solution brief §13) has no UI tier: Unit,
   Property, Contract, Oracle, Injection, and nothing for pages. The harness is
   `streamlit.testing.v1.AppTest` (in `streamlit` itself, so done-when 0 covers it) driving
   pages against a stubbed API client, in `tests/ui/`.

   This is a prerequisite rather than a detail because it decides the shape of the first
   page written: `AppTest` can only assert over pages composed of functions that take data
   and emit elements, not over top-level script code with `st.*` calls interleaved through
   fetching. §13 gains the row.

### The UI

5. Sidebar: persona, trade dates, upload. Same page for every persona.
6. Summary then Specifics; selecting a Summary row drives Specifics. Specifics is
   Why / Impact / Address first; charts only when that persona will look at them.
7. Upload: file → preview / capability disclosure → confirm → progress → dashboard
   updates. Ingest is synchronous by decision (`specs/api-contract.md` §4.4); progress is
   `st.status` around the blocking call, not a job table. Unavailable capabilities
   explained in place (e.g. disabled VWAP).
8. Help on named boxes (KPI tiles and headers), one sentence; skip Why / Impact /
   Address rows and the findings What column.
9. Address is suggestion **text**. No apply or override buttons. `GET /v1/insights/suggestions`
   ships in slice 6, not slice 4 ([04-api.md](04-api.md), Sequencing), so the Analyst
   Specifics view depends on a route that lands after this slice. The plan
   already sequences Analyst last (below); build it against the slice 6 route rather than
   stubbing suggestion text in the UI, which would put copy in a widget that belongs to
   `quality`.

10. **Two Analyst elements had no backing; both are now settled in spec.** Neither blocks
    chrome + Risk or Trader, and neither was recorded in slice 6, whose done-whens are
    `REC.*`, patterns, suggestions, the two routes and injection. Settled here rather than
    left open, because the Analyst screen is built last and the cost of discovering them
    then is a stalled slice.

    - **Raw neighbourhood is daily-grain in v1.** Analyst Specifics opens a raw
      neighbourhood on the selected finding, and no endpoint returns raw market records —
      the contract has no records or neighbourhood route at all. `GET /v1/analytics/bars/daily`
      on `basis=raw`, windowed around the finding, is the whole mechanism. It covers
      `VAL.close` — the UI spec's own worked example — and every other daily-grain finding.
      The minute-grain cases are not served: `CMP.gap` needs the expected slot grid against
      actual records, `REC.vol` needs both frequencies row by row. Those show the finding's
      own evidence (the What column, from `dq.dq_finding.details`) plus the charts, and the
      panel states which grain it is showing rather than rendering empty. A raw-records
      route is the extension that lifts it. Written into `specs/loupe-ui-design.md`, Analyst
      Specifics — the promise is narrowed in the spec, not quietly under-built.

    - **Worst field is derived from rule identity.** `dq.dq_finding` has no field column;
      the field sits in `details`, which `specs/data-model.md` and
      [ddl.sql:182](src/loupe/data/ddl.sql#L182) both put off limits as a grouping key. So
      `RULE_SUBJECT_FIELD` maps rules on a two-part test — the rule asserts a **defect**, and
      fixes the **field that defect is in** — and lives beside `SETTLEMENT_RULES` in the
      catalogue for the same reason. So `CON.CLOSE_OUT_OF_RANGE` → close, all `TIM.*` →
      timestamp, the volume rules → volume. Three groups are deliberately absent and do not
      contribute: field-parametric (`CMP.NULL_FIELD`, `VAL.OFF_TICK_PRICE`,
      `CON.HIGH_LT_LOW`), record-shaped (all `UNQ.*`, `CMP.SESSION_MISSING`,
      `CMP.MISSING_TIMESTAMP` — a run of slots with no record is an absence, not a bad
      timestamp), and diagnostic-not-defect (`OUT.*`, always `info` per §10). The tile reads
      "not applicable" rather than inventing a field when a scope holds only unmapped
      findings. Spec'd at `specs/dq-rules-and-scoring.md` §11.7.

## Sequencing

Done-when 0, 3 and 4 → chrome + Risk → done-when 1 and 2 → Trader → Analyst.

Done-when 0, 3 and 4 come first and are not optional: they are the dependency, the client
module and the test harness, and no page can be written — or written in a testable shape —
until all three exist. None of them is UI code.

Risk then needs neither the changelog nor the rollup for its first screen, so those two API
prerequisites do not block first light; they land before Trader, which is the persona that
needs the changelog panel. Analyst stays last, against slice 6's suggestions route.

Done-when 10 is settled in spec ahead of the build, so Analyst has no open design
questions left when its turn comes — only the slice 6 suggestions route to wait on.

That this slice edits `api` and `quality` is the established pattern, not an exception:
slice 4 edited `insights/gate.py` for the capability state its handlers needed
([04-api.md](04-api.md), done-when 7), and slice 6 adds two routes to the app slice 4 built
([06-rec-suggestions-demo.md](06-rec-suggestions-demo.md), done-when 4). The rule is that
the maths lands in the layer that owns it, not that a slice touches one package.

## Tests

Persona switch changes Summary columns; upload preview before commit; VWAP disabled
with reason on daily-only; no apply/override controls in the tree.

Page tests are `AppTest` over a stubbed client, so they assert view assembly and never
reach DuckDB.

For the prerequisites: the changelog route returns counts per rule × trade date × action,
is read-only, and defaults to the latest succeeded run;
a contract holding both frequencies rolls up to its worst slice score, and to its only slice
score when it holds one; `top_issue` is per contract and not the scope-wide list;
`settlement_issue` draws only from `SETTLEMENT_RULES` at daily grain, so a contract whose
worst issue is a `TIM` smear still shows its closing-day callout, and a minute-only contract
shows an em dash rather than a `CMP.MISSING_TIMESTAMP` standing in for a settlement
(`specs/dq-rules-and-scoring.md` §11.6). `ATTN` follows severity, so a contract with a
middling score and only low-severity findings reads `OK`, and Book hit counts exactly the
`ATTN` rows. `/dq/metrics?group_by=day&dimension=completeness&frequency=daily` returns the
settlement trend, and the unfiltered call still averages dimensions as before.

For done-when 10: a daily-grain finding opens a neighbourhood and a minute-grain one shows
evidence plus charts, naming the grain, rather than erroring or rendering empty; the
worst-field tile is derived from rule identity with no query grouping on
`dq.dq_finding.details`, and reads "not applicable" when a scope's findings are all from
unmapped rules.
